Introduction

このガイドについて

DSL ゼロ。既存テストからスペックを自動生成する最も手軽なアプローチ

🎯 rspec-openapi とは

このガイドでは rspec-openapi を使います。これは 既存の RSpec テストを一切変更せず、テストを実行するだけで OpenAPI スペックを自動生成する gem です。RSwag のような特別な DSL は一切不要です。

🧠 3つのアプローチの位置づけ

Design-First（手書き YAML）：最も正確。並行開発向き。でも YAML を書く手間がかかる。

Code-First / RSwag：テストに DSL でスキーマを書く。テスト = ドキュメント。

Code-First / rspec-openapi（本ガイド）：既存テストをそのまま使う。設定ほぼゼロ。最も手軽。

📋 こんな人に向いています

  • 既存の Rails API にスペックを後付けしたい
  • RSwag の DSL を覚えるのが面倒
  • とにかく手軽に始めたい
  • 既に RSpec のリクエストスペックが書いてある

⚠️ 注意点

rspec-openapi はテスト実行時のリクエスト・レスポンスから型を推測します。そのため、RSwag ほどスキーマの詳細制御はできません（description、example、operationId の自動生成には限界があります）。スペック生成後に手動で微調整が必要な場合もあります。

Chapter 01

rspec-openapi の特徴

RSwag との違いと仕組みを理解する

仕組み

rspec-openapi は、RSpec のリクエストスペック実行時に 実際のリクエストとレスポンスを傍受し、そこから OpenAPI スペックを自動生成します。つまり、「テストで実際に送ったデータ」と「実際に返ってきたデータ」からスキーマを推測するのです。

🧠 たとえ話

RSwag は「注文書（DSL）に詳しく書いてもらって、その通りに伝票（スペック）を作る」アプローチ。

rspec-openapi は「実際の取引（テスト実行）を観察して、そこから伝票（スペック）を自動作成する」アプローチ。注文書を書く手間がゼロですが、観察から推測するので細かいニュアンスが失われることがあります。

RSwag との比較

観点RSwagrspec-openapi
テストの書き方専用 DSL（path, get, response, schema...）普通の RSpec そのまま
学習コストDSL を覚える必要ありほぼゼロ
既存テストの再利用書き直しが必要そのまま使える
スキーマの精度◎ 手動で詳細に定義△ レスポンスから推測
description / exampleDSL で自由に記述テスト名から自動推測
Swagger UI内蔵別途設置が必要
スペック生成コマンドrake rswag:specs:swaggerizeOPENAPI=1 rspec
✅ 使い分けの指針

「既存テストが大量にある」 → rspec-openapi（書き直し不要）
「新規プロジェクトで詳細なドキュメントが必要」 → RSwag
「まず rspec-openapi で始めて、後から RSwag に移行」 も有効な戦略です。

モデルとコントローラを実装

まず動く API を作る ─ 全 CRUD アクションを実装

モデルの生成とマイグレーション

Terminal
rails g model Task title:string description:text status:string
rails db:create db:migrate

# テスト用 DB にも適用（テスト実行前に必要）
RAILS_ENV=test rails db:migrate
app/models/task.rb
class Task < ApplicationRecord
  validates :title, presence: true, length: { maximum: 255 }
  validates :status, inclusion: { in: %w[pending in_progress completed] }, allow_nil: true

  after_initialize { self.status ||= "pending" }

  scope :filter_by_status, ->(status) { where(status: status) if status.present? }
end

ルーティング

config/routes.rb
Rails.application.routes.draw do
  get "up" => "rails/health#show", as: :rails_health_check

  namespace :api do
    namespace :v1 do
      resources :tasks
    end
  end
end

コントローラ（全 CRUD）

app/controllers/api/v1/tasks_controller.rb
module Api
  module V1
    class TasksController < ApplicationController
      before_action :set_task, only: %i[show update destroy]

      def index
        tasks = Task.filter_by_status(params[:status]).order(created_at: :desc)
        render json: tasks
      end

      def show
        render json: @task
      end

      def create
        task = Task.new(task_params)
        if task.save
          render json: task, status: :created
        else
          render json: { errors: task.errors.full_messages }, status: :unprocessable_entity
        end
      end

      def update
        if @task.update(task_params)
          render json: @task
        else
          render json: { errors: @task.errors.full_messages }, status: :unprocessable_entity
        end
      end

      def destroy
        @task.destroy
        head :no_content
      end

      private

      def set_task
        @task = Task.find(params[:id])
      rescue ActiveRecord::RecordNotFound
        render json: { error: "Task not found" }, status: :not_found
      end

      def task_params
        params.require(:task).permit(:title, :description, :status)
      end
    end
  end
end
📌 ポイント

filter_by_status スコープを使って ?status=pending のようなクエリパラメータでフィルタリングできます。task_params で Strong Parameters を使い、:task キーのネストを必須にしています（テストでも { task: { title: "..." } } の形で送信します）。

Chapter 06

普通の RSpec テストを書く

★ 特別な DSL は一切不要。いつものテストをそのまま
🧠 これが rspec-openapi 最大の特徴

RSwag では path "/api/v1/tasks" do、get "説明" do、schema type: :array のような専用 DSL が必要でした。rspec-openapi では、普通の RSpec リクエストスペックをそのまま書くだけです。特別なメソッドは何も使いません。

最もシンプルなテスト例

spec/requests/api/v1/tasks_spec.rb（抜粋）
require "rails_helper"  # ← openapi_helper ではない！普通の rails_helper

RSpec.describe "Tasks API", type: :request do

  describe "GET /api/v1/tasks" do
    it "returns a list of tasks" do
      # ── テストデータ ──
      Task.create!(title: "タスク1", status: "pending")
      Task.create!(title: "タスク2", status: "completed")

      # ── リクエスト ──
      get "/api/v1/tasks"

      # ── アサーション ──
      expect(response).to have_http_status(200)
      json = JSON.parse(response.body)
      expect(json.length).to eq(2)
    end
  end
end

これだけです。RSwag のような path、tags、produces、schema、run_test! は一切ありません。

何が起きるのか？

OPENAPI=1 をつけてテストを実行すると、rspec-openapi が裏で以下を行います。

  1. テスト中の get "/api/v1/tasks" を傍受して、パス・メソッドを記録
  2. 実際のレスポンスボディを解析して、スキーマ（型）を推測
  3. テスト名（"returns a list of tasks"）を description として使用
  4. 全テスト終了後に、これらの情報を doc/openapi.yaml に出力
✅ テストの書き方のコツ

rspec-openapi はテスト実行時のレスポンスからスキーマを推測するので、テストデータがスキーマの品質を左右します。

全フィールドが埋まったデータを使うと、より正確なスキーマが生成されます。たとえば description: nil のデータしかないと、description が nullable として推測されます。

Chapter 07

全 CRUD のテスト

全エンドポイントを網羅するテストを書く
⚠️ Strong Parameters のネストに注意

コントローラで params.require(:task).permit(...) としているため、POST/PATCH リクエストのボディは { "task": { "title": "..." } } のように task キーでネストして送る必要があります。テストでも同様に { task: { ... } }.to_json の形で送信します。

spec/requests/api/v1/tasks_spec.rb（完全版）
require "rails_helper"

RSpec.describe "Tasks API", type: :request do
  let(:json) { JSON.parse(response.body) }

  # ── 一覧取得 ──
  describe "GET /api/v1/tasks" do
    it "returns all tasks" do
      Task.create!(title: "タスク1", description: "詳細1", status: "pending")
      Task.create!(title: "タスク2", description: "詳細2", status: "completed")

      get "/api/v1/tasks"

      expect(response).to have_http_status(200)
      expect(json.length).to eq(2)
      expect(json[0]).to have_key("id")
      expect(json[0]).to have_key("title")
      expect(json[0]).to have_key("status")
      expect(json[0]).to have_key("created_at")
    end

    it "filters by status" do
      Task.create!(title: "やること", status: "pending")
      Task.create!(title: "終わった", status: "completed")

      get "/api/v1/tasks", params: { status: "pending" }

      expect(response).to have_http_status(200)
      expect(json.length).to eq(1)
      expect(json[0]["status"]).to eq("pending")
    end

    it "returns empty array when no tasks exist" do
      get "/api/v1/tasks"
      expect(response).to have_http_status(200)
      expect(json).to eq([])
    end
  end

  # ── 詳細取得 ──
  describe "GET /api/v1/tasks/:id" do
    it "returns a task" do
      task = Task.create!(title: "テスト", description: "メモ", status: "in_progress")
      get "/api/v1/tasks/#{task.id}"

      expect(response).to have_http_status(200)
      expect(json["id"]).to eq(task.id)
      expect(json["status"]).to eq("in_progress")
    end

    it "returns 404 for not found" do
      get "/api/v1/tasks/999999"
      expect(response).to have_http_status(404)
      expect(json).to have_key("error")
    end
  end

  # ── 作成 ──
  describe "POST /api/v1/tasks" do
    it "creates a task" do
      # ★ task: キーでネストして送る
      post "/api/v1/tasks",
        params: { task: { title: "新しいタスク", description: "メモ" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(201)
      expect(json["title"]).to eq("新しいタスク")
      expect(json["status"]).to eq("pending")
    end

    it "creates a task with status" do
      post "/api/v1/tasks",
        params: { task: { title: "進行中タスク", status: "in_progress" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(201)
      expect(json["status"]).to eq("in_progress")
    end

    it "returns 422 for missing title" do
      post "/api/v1/tasks",
        params: { task: { title: "" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(422)
      expect(json).to have_key("errors")
    end

    it "returns 422 for invalid status" do
      post "/api/v1/tasks",
        params: { task: { title: "タスク", status: "invalid" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(422)
      expect(json).to have_key("errors")
    end
  end

  # ── 更新 ──
  describe "PATCH /api/v1/tasks/:id" do
    it "updates a task" do
      task = Task.create!(title: "元のタイトル", status: "pending")
      patch "/api/v1/tasks/#{task.id}",
        params: { task: { title: "更新後", status: "in_progress" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(200)
      expect(json["title"]).to eq("更新後")
      expect(json["status"]).to eq("in_progress")
    end

    it "returns 422 for invalid update" do
      task = Task.create!(title: "タスク")
      patch "/api/v1/tasks/#{task.id}",
        params: { task: { title: "" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(422)
      expect(json).to have_key("errors")
    end

    it "returns 404 for not found" do
      patch "/api/v1/tasks/999999",
        params: { task: { title: "更新" } }.to_json,
        headers: { "Content-Type" => "application/json" }

      expect(response).to have_http_status(404)
    end
  end

  # ── 削除 ──
  describe "DELETE /api/v1/tasks/:id" do
    it "deletes a task" do
      task = Task.create!(title: "削除対象")
      delete "/api/v1/tasks/#{task.id}"

      expect(response).to have_http_status(204)
      expect(Task.find_by(id: task.id)).to be_nil
    end

    it "returns 404 for not found" do
      delete "/api/v1/tasks/999999"
      expect(response).to have_http_status(404)
    end
  end
end
🧠 RSwag との比較

上のコードに OpenAPI 固有のメソッドは一つもありません。tags、schema、operationId、run_test! のどれも使っていません。100% 純粋な RSpec です。

これが rspec-openapi の最大の利点です。既存のテストをそのまま使えるので、移行コストがほぼゼロです。

Chapter 08

rspec-openapi の設定

生成されるスペックをカスタマイズする

設定ファイルの作成

デフォルトでも動きますが、設定を追加すると生成されるスペックの品質が上がります。

⚠️ バージョンによる設定名の違い

古い記事や生成AIの回答では tag_builder=・target_request_metadata= と書かれている場合がありますが、rspec-openapi 0.27.x では存在しないメソッドです。実際のメソッド名は下表の通りです。

spec/openapi_helper.rb（新規作成）
require "rspec/openapi"

# ── 出力先のパス ──
RSpec::OpenAPI.path = "doc/openapi.yaml"

# ── API のメタ情報 ──
RSpec::OpenAPI.title = "Task Manager API"
RSpec::OpenAPI.info = {
  version: "1.0.0",
  description: "タスク管理アプリケーションの API"
}
RSpec::OpenAPI.servers = [
  { url: "http://localhost:3000", description: "開発環境" }
]

# ── 対象を request spec のみに限定（正しい設定名: example_types）──
RSpec::OpenAPI.example_types = [:request]

# ── タグをパス末尾から生成（正しい設定名: tags_builder）──
# /api/v1/tasks → ["Tasks"] になる
RSpec::OpenAPI.tags_builder = ->(example) {
  path = example.metadata[:request_path] || ""
  [path.split("/").reject(&::empty?).last&.capitalize].compact
}
spec/spec_helper.rb に追記
# spec_helper.rb の先頭に追加
require_relative "openapi_helper" if ENV["OPENAPI"]

主な設定項目（rspec-openapi 0.27.x）

設定デフォルト説明
RSpec::OpenAPI.path"doc/openapi.yaml"スペックの出力先
RSpec::OpenAPI.title"OpenAPI"API のタイトル
RSpec::OpenAPI.info{}version / description などのメタ情報
RSpec::OpenAPI.servers[]サーバーの URL 一覧
RSpec::OpenAPI.example_types[:request]対象 spec タイプ（旧: target_request_metadata）
RSpec::OpenAPI.tags_builderコントローラ名タグ生成ロジック（旧: tag_builder）
RSpec::OpenAPI.request_headers[]記録するリクエストヘッダー
RSpec::OpenAPI.response_headers[]記録するレスポンスヘッダー
✅ テスト名が description になる

it "returns a list of tasks" のテスト名が、生成されるスペックの summary や description に自動的に使われます。テスト名を分かりやすく書くことが、良いドキュメントにつながります。

Chapter 09

スペック自動生成と確認

OPENAPI=1 をつけてテストを実行するだけ

生成コマンド

Terminal
# ★ これだけ！環境変数 OPENAPI=1 をつけて rspec 実行
OPENAPI=1 bundle exec rspec

# → doc/openapi.yaml が自動生成される
cat doc/openapi.yaml
🧠 OPENAPI=1 の意味

普段のテスト実行（bundle exec rspec）ではスペックは生成されません。OPENAPI=1 をつけたときだけ生成モードになります。これにより、CI のテスト実行速度に影響を与えません。

生成されたスペックの確認

rspec-openapi が生成するスペックは、テスト実行時のレスポンスから型を推測するため、完璧ではない場合があります。以下のポイントを確認してください。

  • nullable の検出：description が nil のテストデータがあれば nullable: true が推測される。全フィールドが埋まったデータだけだと検出されない
  • enum の検出：rspec-openapi は enum を自動検出しない。手動で追加する必要がある場合がある
  • required の推測：レスポンスに常に含まれるフィールドは required と推測される
⚠️ 必要に応じて手動調整

生成された doc/openapi.yaml は手動で微調整できます。ただし、次回 OPENAPI=1 rspec を実行するとマージされます（完全な上書きではなく、既存の内容に追記・更新されます）。手動で追加した enum や description は保持されます。

Chapter 16

components へのスキーマ分割

生成された YAML を $ref で整理して再利用性を高める

なぜ分割するのか

rspec-openapi が生成する YAML は、各エンドポイントのレスポンスボディのスキーマがそのままインラインで展開されます。同じ Task オブジェクトのスキーマが GET/POST/PATCH すべてに重複して記述されるため、スキーマを変更したい場合に修正箇所が複数になります。

components/schemas に共通スキーマを定義して $ref で参照することで、単一箇所の変更で全エンドポイントに反映できます。

🧠 生成直後 vs 分割後のイメージ

生成直後：各 responses にスキーマがインライン展開されている。Task の定義が3〜4箇所に重複。

分割後：components/schemas/Task に一箇所定義し、各 responses から $ref: '#/components/schemas/Task' で参照する。

生成直後のYAML（インライン展開）

doc/openapi.yaml（生成直後 — 抜粋）
paths:
  /api/v1/tasks:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  type: object          # ← ここにインラインで定義
                  properties:
                    id: { type: integer }
                    title: { type: string }
                    description: { type: string, nullable: true }
                    status: { type: string }
                    created_at: { type: string }
                    updated_at: { type: string }
  /api/v1/tasks/{id}:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object          # ← 同じ定義がまた出てくる
                properties:
                  ...

分割後のYAML

doc/openapi.yaml（分割後）
paths:
  /api/v1/tasks:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Task'   # ← $ref で参照
  /api/v1/tasks/{id}:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Task'   # ← 同じ $ref

components:
  schemas:
    Task:                                         # ← ここに一元定義
      type: object
      required:
        - id
        - title
        - status
        - created_at
        - updated_at
      properties:
        id:
          type: integer
        title:
          type: string
          maxLength: 255
        description:
          type: string
          nullable: true
        status:
          type: string
          enum:                                   # ← 手動で enum を追加
            - pending
            - in_progress
            - completed
        created_at:
          type: string
          format: date-time
        updated_at:
          type: string
          format: date-time

    ErrorResponse:                               # ← エラー形式も共通化
      type: object
      required:
        - errors
      properties:
        errors:
          type: array
          items:
            type: string

    TaskInput:                                    # ← リクエストボディ用
      type: object
      required:
        - title
      properties:
        title:
          type: string
        description:
          type: string
          nullable: true
        status:
          type: string
          enum: [pending, in_progress, completed]
✅ 手動調整は OPENAPI=1 実行後にマージされる

rspec-openapi は OPENAPI=1 rspec 実行時に既存の YAML とマージ（差分適用）します。components/schemas に手動で追加した内容は保持されます。ただし、インライン展開の箇所を $ref に書き換えた場合、再生成時に上書きされる可能性があるため、分割作業は生成が落ち着いた後に行うのがおすすめです。

リクエストボディへの $ref 適用

POST / PATCH のリクエストボディも同様に $ref で参照できます。

POST のリクエストボディ（分割後）
  /api/v1/tasks:
    post:
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/TaskInput'
      responses:
        '201':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Task'
        '422':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/ErrorResponse'

shared_examples でレスポンス構造を共通化

複数のエンドポイントで同じ「Task オブジェクトが返る」アサーションを繰り返すなら、shared_examples にまとめられます。

RSpec.shared_examples "a task response" do
  let(:json) { JSON.parse(response.body) }

  it "includes required task fields" do
    expect(json).to include(
      "id" => be_a(Integer),
      "title" => be_a(String),
      "status" => be_in(%w[pending in_progress completed]),
      "created_at" => be_a(String)
    )
  end
end
使い方
describe "GET /api/v1/tasks/:id" do
  it "returns a task" do
    task = Task.create!(title: "テスト")
    get "/api/v1/tasks/#{task.id}"

    expect(response).to have_http_status(200)
    include_examples "a task response"
  end
end

JSON ヘルパーを let で共有

RSpec.configure do |config|

  config.include(Module.new {
    def json
      JSON.parse(response.body)
    end

JSON リクエストヘルパー

POST / PATCH で毎回 headers: { "Content-Type" => "application/json" } を書くのは冗長です。ヘルパーメソッドにまとめましょう。

spec/support/request_helpers.rb
module RequestHelpers
  def json_post(path, params: {})
    post path,
      params: params.to_json,
      headers: { "Content-Type" => "application/json" }
  end

  def json_patch(path, params: {})
    patch path,
      params: params.to_json,
      headers: { "Content-Type" => "application/json" }
  end
end

RSpec.configure do |config|
  config.include RequestHelpers, type: :request
end
ヘルパー使用後のテスト
it "creates a task" do
  json_post "/api/v1/tasks", params: { task: { title: "新しいタスク" } }

  expect(response).to have_http_status(201)
  expect(json["title"]).to eq("新しいタスク")
end

✅ 実践的な判断基準

外部公開 API / 大規模チーム → Design-First（スペックが契約書）

新規の社内 API / 中規模チーム → Code-First（RSwag）

  • CI での整合性チェック
